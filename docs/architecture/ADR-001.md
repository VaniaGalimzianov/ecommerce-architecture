# ADR-001: Выбор архитектурного стиля системы интернет-магазина

## Статус

Accepted

## Дата

2026-09-27

## Контекст

Разрабатывается система интернет-магазина — REST API для продажи товаров онлайн. Система должна обеспечивать:

- каталог товаров (просмотр, поиск, фильтрация, управление для админа);
- оформление и оплату заказов;
- регистрацию и аутентификацию пользователей;
- интеграцию с внешними системами: платежный шлюз, служба доставки, SMS/Email-нотификатор;
- асинхронную обработку уведомлений.

Ограничения проекта:

- команда разработки из трех человек;
- необходимость масштабирования при росте нагрузки;
- требование сопровождаемости и расширяемости.

Требуется выбрать архитектурный стиль, который обеспечит баланс между скоростью разработки, стоимостью, надежностью и возможностью роста.

### Учитываемые показатели

- **Time-to-Market** — скорость выхода на рынок.
- **Scalability** — способность масштабироваться при росте нагрузки.
- **Cost** — стоимость разработки и эксплуатации.
- **Reliability** — надежность и отказоустойчивость.
- **Maintainability** — простота сопровождения и развития.

### Рассматриваемые варианты

1. **Монолит** — единое приложение без четких внутренних границ.
2. **Модульный монолит** — единое приложение с четкими модулями (catalog, orders, users, payments, notifications).
3. **Микросервисы** — набор независимых сервисов, каждый со своим жизненным циклом.

### Сравнение

| Критерий | Монолит | Модульный монолит | Микросервисы |
|---|---|---|---|
| Time-to-Market | высокий | высокий | низкий |
| Scalability | низкая | средняя | высокая |
| Cost | низкая | низкая | высокая |
| Reliability | низкая | средняя | высокая* |
| Maintainability | низкая | высокая | средняя |

\* Высокая надежность микросервисов достигается только при зрелой инфраструктуре (оркестрация, мониторинг). Без нее надежность ниже, чем у монолита.

### Комментарии по критериям

**Time-to-Market.**
Монолит и модульный монолит стартуют быстро: одна кодовая база, один деплой, нет распределенных транзакций. Микросервисы требуют настройки инфраструктуры, CI/CD, мониторинга, координации между модулями — это замедляет старт.

**Scalability.**
Микросервисы масштабируются точечно (только нагруженный сервис). Модульный монолит масштабируется целиком, но это проще и дешевле на ранних этапах. Монолит без модулей масштабировать сложнее из-за связанности.

**Cost.**
Монолит и модульный монолит дешевле: одна инфраструктура, один деплой, меньше DevOps-нагрузки. Микросервисы требуют больше серверов, больше мониторинга, больше людей.

**Reliability.**
Микросервисы изолируют сбои: падение одного сервиса не роняет все. Но добавляют распределенные сбои (сеть, таймауты, частичные отказы). Монолит — единая точка отказа, но проще в отладке.

**Maintainability.**
Модульный монолит дает четкие границы модулей при единой кодовой базе — легко понимать и развивать. Микросервисы сложнее в сопровождении: распределенные логи, трассировка, версионирование API. Монолит без границ со временем превращается в тяжело управляемый сервис.

## Решение

Выбран **модульный монолит**.

Обоснование:

- **Быстрый старт.** Одна кодовая база, один деплой, нет распределенных транзакций — команда быстро выпускает MVP.
- **Низкая стоимость.** Одна инфраструктура, минимум DevOps.
- **Четкие границы.** Модули изолированы, что упрощает развитие и тестирование.
- **Возможность роста.** При необходимости модули можно вынести в отдельные сервисы без переписывания всей системы с нуля.

Первыми кандидатами на вынос в отдельные сервисы определены:

1. **Платежи (Payments).** Требует изоляции по безопасности, отдельного масштабирования, интеграции с внешним шлюзом.
2. **Уведомления (Notifications).** Асинхронная обработка, независимое масштабирование, интеграция с внешним SMS/Email-сервисом.

Эти модули уже сейчас взаимодействуют с остальной системой через асинхронные события (RabbitMQ), что упрощает их будущий вынос.

## Последствия

### Положительные

- Быстрый релиз.
- Низкая стоимость разработки и эксплуатации.
- Простота разработки, деплоя и отладки.
- Четкие границы модулей упрощают сопровождение и тестирование.
- Возможность постепенного выноса сервисов без переписывания системы.
- Асинхронные модули (уведомления, остатки) уже работают через брокер, что готовит основу для будущего выделения.

### Отрицательные

- Ограниченная масштабируемость: масштабируется все приложение целиком, а не отдельные модули.
- Единая точка отказа: падение приложения роняет всю систему.
- Риск потери границ модулей: без дисциплины границы модулей размываются.

## Риски

| № | Риск | Вероятность | Влияние | Мера снижения |
|---|------|-------------|---------|---------------|
| 1 | Расползание модульного монолита — границы модулей размываются со временем | Средняя | Высокое | Четкие интерфейсы между модулями, code review, архитектурные тесты, регулярный рефакторинг |
| 2 | Единая точка отказа — падение приложения роняет всю систему | Средняя | Высокое | Горизонтальное масштабирование (несколько инстансов), health checks, автоматический рестарт, балансировка нагрузки |
| 3 | Замедление разработки со временем — рост кодовой базы усложняет изменения | Средняя | Среднее | Четкие границы модулей, регулярный рефакторинг, code review |
| 4 | Сложность будущего выноса сервисов — границы модулей могут оказаться не готовы к выделению | Низкая | Среднее | Дисциплина в реализации сервиса, четкое разделение модулей и рефакторинг, проектирование с учетом будущего выноса |
| 5 | Нехватка мощности при пике — единое приложение не справляется с нагрузкой | Средняя | Высокое | Горизонтальное масштабирование, кэширование, нагрузочное тестирование заранее |
